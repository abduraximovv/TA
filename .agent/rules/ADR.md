# Architecture Decision Records (ADR) - SmartOps ERP

## Введение для AI-Агентов
Этот документ содержит фундаментальные архитектурные решения проекта SmartOps ERP. 
**Ты ОБЯЗАН неукоснительно следовать этим правилам при написании архитектурного кода, API, миграций баз данных и бизнес-логики.** Любое отклонение от этих решений запрещено без явного разрешения пользователя.

---

### ADR-001: Архитектурный паттерн — Модульный Монолит (Modular Monolith)
**Статус:** Принято
**Контекст:** 
Разработка микросервисной архитектуры на старте проекта вносит избыточную сложность (accidental complexity), сетевые задержки и усложняет транзакционность финансовых операций [2]. Для небольшой команды важна скорость разработки с возможностью масштабирования в будущем.
**Решение:**
Мы используем паттерн **Модульный Монолит** с применением Вертикальной архитектуры (Vertical Slice Architecture) [3]. Весь код находится в одном репозитории и разворачивается как единое целое.
**Следствия и Правила для кода:**
1. Код должен быть строго разделен по доменам: `src/modules/inventory`, `src/modules/finance`, `src/modules/crm` [4].
2. Модули **НЕ ИМЕЮТ ПРАВА** напрямую обращаться к таблицам БД или внутренним функциям других модулей.
3. Межмодульное взаимодействие происходит ТОЛЬКО через публичные интерфейсы (API модуля) или через систему событий (Event Bus).

### ADR-002: Мультиарендность (Multi-tenancy) и Изоляция Данных
**Статус:** Принято
**Контекст:** 
SmartOps — это SaaS ERP. Данные множества компаний (клиентов) хранятся в одной базе данных. Утечка данных одного клиента к другому недопустима.
**Решение:**
Использование архитектуры **Shared Database** с изоляцией на уровне СУБД через **Row-Level Security (RLS)** в PostgreSQL (Supabase) [5, 6].
**Следствия и Правила для кода:**
1. В **каждой** таблице (кроме системных словарей) ОБЯЗАТЕЛЬНО должна быть колонка `organization_id` (UUID).
2. Безопасность не должна контролироваться только на фронтенде или в API. При создании новой таблицы (миграции) **всегда** генерируй политику RLS, ограничивающую доступ по `organization_id` [6].
3. ИИ-агенту запрещено предлагать создание изолированных баз данных для каждого клиента (Database per Tenant).

### ADR-003: Финансовая точность и типы данных
**Статус:** Принято
**Контекст:** 
Использование чисел с плавающей точкой (Float/Double) для финансовых вычислений приводит к ошибкам округления, что катастрофично для ERP-системы [7].
**Решение:**
Все денежные суммы и финансовые транзакции хранятся в целочисленном формате (**BIGINT**) в минимальных единицах валюты (например, в тийинах или центах) [7].
**Следствия и Правила для кода:**
1. Никогда не используй тип `FLOAT`, `REAL` or `DOUBLE PRECISION` в таблицах PostgreSQL, содержащих деньги.
2. В TypeScript все финансовые переменные должны обрабатываться с учетом того, что это целые числа.
3. Конвертация в "человеческий" вид (например, 100.50) происходит ТОЛЬКО на слое представления (UI/Frontend).

### ADR-004: Устойчивость к медленному интернету (Offline-First UX)
**Статус:** Принято
**Контекст:** 
Целевая аудитория работает на складах и производствах в Узбекистане, где часто встречается нестабильный 3G интернет. Ожидание ответа сервера при каждом клике убьет пользовательский опыт.
**Решение:**
Агрессивное кэширование на клиенте и паттерн **Optimistic UI**.
**Следствия и Правила для кода:**
1. Для всех запросов на получение данных использовать `TanStack Query` (React Query) с кэшированием (staleTime).
2. При мутациях (создание заказа, списание товара) использовать Optimistic Updates: обновлять интерфейс ДО получения подтверждения от сервера.
3. **Идемпотентность:** Все ID для новых записей (`UUID`) должны генерироваться **на клиенте** перед отправкой запроса к Supabase. Это предотвратит создание дублей, если пользователь несколько раз нажмет кнопку при плохом интернете.

### ADR-005: Целостность данных (ACID и Аудит)
**Статус:** Принято
**Контекст:** 
В ERP данные о транзакциях и складских перемещениях не должны бесследно исчезать или обновляться без следа.
**Решение:**
Принцип "Мягкого удаления" (Soft Deletes) и транзакционности [8].
**Следствия и Правила для кода:**
1. **Никаких физических удалений:** Запрещено использовать SQL команду `DELETE` для бизнес-сущностей. Все таблицы должны иметь колонку `deleted_at` (Timestamp) или `is_active` (Boolean) [8].
2. Транзакционность: Любая бизнес-операция, затрагивающая более одной таблицы (например, подтверждение заказа + списание товара со склада), **обязана** выполняться внутри одной транзакции базы данных [8].
3. Аудит: Добавлять к записям поля `created_by` и `updated_by` для отслеживания, кто совершил действие.

### ADR-006: Гибкость характеристик без потери производительности (JSONB)
**Статус:** Принято
**Контекст:** 
Разным бизнесам нужны разные поля для товаров (цвет, размер, вес, напряжение). Создание отдельных таблиц для каждого атрибута (EAV паттерн) или изменение схемы таблицы `products` при каждом новом клиенте сильно ударит по производительности [9].
**Решение:**
Полиглотно-персистентный подход с использованием типа `JSONB` в PostgreSQL [9, 10].
**Следствия и Правила для кода:**
1. Для гибких или специфичных характеристик сущностей (товаров, профилей клиентов) использовать колонку `attributes` с типом данных `JSONB`.
2. Базовые поля для поиска и фильтрации (SKU, название, цена) должны оставаться строгими реляционными колонками.

### ADR-007: Шаблон "Transactional Outbox" для надежной асинхронной интеграции
**Статус:** Принято
**Контекст:**
При фиксации заказов (Checkout) или складских движений необходимо отправлять уведомления и генерировать асинхронные бизнес-события (например, `OrderCompleted`). Отправка событий напрямую из API-кода Next.js до фиксации транзакции БД создает риск рассинхронизации: если транзакция откатится, событие уже улетит. Если же отправка события упадет с сетевой ошибкой, бизнес-операция не должна отменяться.
**Решение:**
Мы внедряем паттерн **Transactional Outbox**. Бизнес-события записываются в специальную таблицу `outbox_events` внутри той же ACID транзакции СУБД, которая фиксирует основные изменения домена. Отдельный фоновый воркер надежно опрашивает `outbox_events` и доставляет события внешним подписчикам с гарантией at-least-once.
**Следствия и Правила для кода:**
1. Все интеграционные события домена (Sales, Inventory) обязаны записываться в `outbox_events` внутри единого RPC транзакции.
2. Исключить отправку писем, вебхуков или брокеров сообщений напрямую из тела Server Actions.

### ADR-008: Использование SECURITY DEFINER RPC в PostgreSQL для ACID операций
**Статус:** Принято
**Контекст:**
Сложные транзакции (такие как списание по FIFO, BOM разузлование при продаже комплектов, начисление долга Nasiya с проверкой лимита) затрагивают множество таблиц и требуют абсолютной атомарности. Выполнение нескольких последовательных запросов по сети из Next.js Server Actions не гарантирует ACID, создает сетевые задержки и уязвимо для race conditions. Более того, строгие RLS политики для роли `authenticated` (worker) блокируют прямую запись в системный аудит-журнал `transactions`.
**Решение:**
Инкапсулировать сложные цепочки операций в PostgreSQL RPC функции с модификатором `SECURITY DEFINER`. Эти функции выполняются от лица владельца БД с обходом RLS таблиц аудита, но при этом обязаны явно проверять `organization_id` пользователя, переданный в параметрах или JWT, и проводить внутреннюю валидацию прав доступа (RBAC).
**Следствия и Правила для кода:**
1. POS Checkout и FIFO списания проводятся через единый Postgres RPC (например, `process_sale_transaction`).
2. Внутренний код RPC обязан быть строго транзакционным (начинаться с `BEGIN` и возвращать ошибку через `RAISE EXCEPTION` для автоматического отката).

### ADR-009: Фиксация версии Vercel AI SDK (3.4.33) для стабильности API
**Статус:** Принято
**Контекст:**
Библиотека Vercel AI SDK активно развивается, и обновления минорных/патч-версий часто содержат несовместимые изменения в механизмах обработки потокового текста (stream protocol) и Zod-генерации структурированных объектов (`generateObject`).
**Решение:**
Зафиксировать версию пакета `ai` строго на уровне `3.4.33` в `package.json` без использования символов `^` или `~`. Все функции AI Onboarding и AI BOM Parsing должны полагаться исключительно на стабильный контракт этой версии.
**Следствия и Правила для кода:**
1. Ни модели, ни разработчики не имеют права обновлять версию пакета `ai` до согласования глобальной архитектуры Next.js 16/React 19 миграции.
2. Все файлы, импортирующие `ai` или `@ai-sdk/react`, обязаны следовать сигнатурам версии `3.4.33`.
